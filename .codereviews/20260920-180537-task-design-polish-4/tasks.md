- [ ] A reading is painted over the maximal kanji run before it, so a partially annotated run tells the learner a wrong reading — with no check able to catch it. — frontend/app/src/lib/furigana.ts:70 !p2
  Furigana notation carries no base length, so `baseOf` guesses "every kanji up to the group". If Claude returns 毎日東京へ行きます with furigana 毎日東京《とうきょう》へ行《い》きます — annotating only the unfamiliar part, which is ordinary furigana convention — the backend's round-trip check passes (stripping the groups reproduces the translation exactly) and the pane renders <ruby>毎日東京<rt>とうきょう</rt></ruby>: the learner is told 毎日東京 reads とうきょう. Same for 新型肺炎《はいえん》, 日本漢字《かんじ》. The module's own tests acknowledge the hole for a base that is too short (the 霞ケ関 case) but nothing catches one that is too long. Note the premise is a model deviation: prompt.rb:83 instructs "the reading of each run of kanji", so this needs Claude to under-annotate — likely enough over many requests, and nothing detects it when it happens.
  Fix: Make the base explicit rather than inferred — have the model emit {base, reading} pairs or delimit the base — or, cheaper, check on the backend that every maximal kanji run in `text` is immediately followed by a 《…》 group and drop the whole furigana string when it isn't, turning an undetectable wrong reading into the clean degrade the module already prefers.

- [ ] A translation legitimately containing 《…》 fails the round-trip check, so every reading in the reply is dropped — and `readingsOmitted` stays false, so nothing accounts for the loss. — backend/app/services/translation/claude_translator.rb:227 !p2
  U+300A/U+300B are ordinary Japanese punctuation (titles, emphasis) and the system prompt tells Claude to keep the original's punctuation style. Translate EN→JA with source `He recommended 《Kokoro》 to me.`: the translation contains 《こころ》 and the furigana contains it too, so `value.gsub(FURIGANA_READING, "")` strips the literal brackets along with the three real readings, the strings no longer match, `furigana_from` returns nil and warns. `Result.for_request` then sets `furigana: nil` with `readings_omitted: japanese && !readings` = false (the source was well inside the limit), so the client shows no ruby and no shortfall sentence, while `Translation.readingsOmitted`'s published description says false means `furigana` is null "because `text` has no kanji" — untrue here. Every reading lost on one stray bracket pair, silently. The prompt's own contract ("removing every 《…》 group must yield the translation") is unsatisfiable for such a translation, so the model cannot get this right.
  Fix: Distinguish "readings were asked for and thrown away" from "never asked for" (a second cause on the flag or a third state) so the pane can say readings were dropped; and stop one bracket destroying the whole annotation — tell the model to return an empty "furigana" when the translation contains 《 or 》, or validate group-by-group instead of with a blanket gsub. At minimum stop the field description claiming length and "no kanji" are the only causes.

- [ ] `Result.for_request` is declared the one place the annotation rules live but enforces only the cap and the furigana gate — three other rules sit at call sites, and FakeTranslator already breaks one of them on the dev/CI path. — backend/app/services/translation/result.rb:41 !p2
  `for_request` gates furigana on target language and caps the gloss list, but never reads `request.gloss_level`, never touches `Gloss#reading`, and never checks that furigana strips back to `text`. Those rules live per-translator: `ClaudeTranslator#glosses_from` (:249) returns [] for NONE and `#gloss_from` (:290) nils `reading` for a non-JA target; `FakeTranslator#glosses_for` (:52) and `#glosses_at` (:79) re-implement both; the strip-back check is in `ClaudeTranslator#furigana_from` alone. The cost is already being paid: run TRANSLATOR=fake (dev, CI, the frontend) with a Japanese target and source `テスト《てすと》` — `text` is `[日本語] テスト《てすと》` and `furigana_for` returns `[日本語《にほんご》] テスト《てすと》`, which strips to `[日本語] テスト`, violating the `furigana` field's published description; the browser's `placedSegments` catches the mismatch and silently shows no ruby. fake_translator_test.rb:20 asserts the invariant for one hard-coded sample, which is why nothing notices. The same shape has bitten this branch twice already (the fake ignoring gloss_level; the fake emitting hundreds of glosses). result_test.rb's header claims the rules hold "including a translator written after this test", true of the cap and the two flags and false of these three.
  Fix: Move all three onto `for_request`, where `request.gloss_level` and the already-computed `japanese` are in hand: return [] for NONE, drop `reading` unless the target is Japanese, and validate strip-back-to-`text` there. Then delete the per-translator copies, as `GlossLocator` already did for span placement.
