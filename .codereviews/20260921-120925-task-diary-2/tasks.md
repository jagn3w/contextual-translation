- [ ] The context cap uses take_while over threads ordered newest first, so the first thread that does not fit also drops every older thread. If the newest thread alone is over MAX_CONTEXT_CHARS, the review gets no thread context at all. — backend/app/services/diary/service.rb:157 !p2
  A thread already over the cap drops every open thread from the next review, and `<feedback_threads>` becomes '(none)'. The learner gets no signal beyond a warn log line. This contradicts docs/diary.md and docs/prompts.md, which say oldest threads are dropped first until the rest fit. The finder's route to an over-cap single thread is contrived: several 2,000-character comments, each answered by a 4,000+ character tutor reply. The mid-list case is more reachable: one large middle thread drops every smaller older thread that would still fit. The harm is lost review context, not lost data. The cap comment's arithmetic (9 x 2,000) also wrongly assumes tutor comments are at most 2,000 characters.
  Fix: Keep a running budget and skip a thread that does not fit, rather than stopping at it, or cap each thread's share. Add a test where the newest thread alone is over the cap.
